## 1. Назначение документа

Настоящее техническое задание описывает назначение, структуру, пользовательские сценарии, функциональные модули, роли, данные, требования к безопасности и целевую архитектуру цифровой платформы «Цифровой наставник».

Документ должен позволить заказчику, проектировщику, разработчику, дизайнеру, системному аналитику, специалисту по информационной безопасности и будущему администратору понять платформу без предварительного знакомства с сайтом.

Техническое задание одновременно фиксирует:

1. фактически реализованные возможности действующего веб-прототипа;
2. назначение и логику каждой вкладки;
3. полный путь пользователя от первого открытия сайта до завершения 90-дневного маршрута;
4. административные процессы;
5. требования к регистрации, авторизации и централизованному хранению данных;
6. требования к обработке персональных данных;
7. целевую модель внедрения ИИ-агента;
8. требования к проверке заданий пользователя ИИ-агентом и администратором;
9. функциональные и нефункциональные критерии приёмки промышленной версии.

> **Важно.** На дату подготовки документа сайт является статическим прототипом. Большая часть пользовательских данных хранится только в браузере посредством `localStorage` и `IndexedDB`. Полноценные аккаунты, серверная база данных, межустройственная синхронизация и защищённый серверный ИИ-контур должны быть реализованы в целевой версии.

## 3. Общая концепция платформы

### 3.1. Идея продукта

«Цифровой наставник» — это единая цифровая рабочая среда для нового или развивающегося специалиста сферы молодёжной политики. Платформа должна не только предоставлять справочные материалы, но и помогать человеку ежедневно применять знания в реальной работе.

Основная идея продукта: **за каждым документом, мероприятием и управленческим решением находится возможность для молодого человека**. Поэтому интерфейс связывает профессиональную адаптацию, практические задания, планирование, базу знаний, инструменты проектирования и поддержку ИИ-агента.

### 3.2. Цель платформы

Сократить время адаптации специалиста, повысить качество самостоятельной работы, обеспечить единый стандарт прохождения первых 90 дней, сделать прогресс прозрачным для пользователя и администратора и предоставить безопасную точку доступа к проверенным материалам отрасли.

### 3.3. Задачи платформы

- провести пользователя через структурированный 90-дневный маршрут;
- ежедневно показывать понятный рабочий фокус;
- дать практические инструменты для подготовки мероприятий, проектов, инициатив и результатов;
- обеспечить доступ к нормативной и методической базе;
- научить пользователя подтверждать результаты своей работы;
- организовать передачу заданий на проверку;
- выполнить ИИ-предпроверку материалов и снизить нагрузку администратора;
- обеспечить администратору очередь заданий, аналитику и контроль прогресса;
- сформировать персональный профиль профессионального развития;
- сохранять историю обучения, решений и обратной связи;
- соблюдать требования к защите ПДн и служебной информации.

### 3.4. Целевая аудитория

1. Новые сотрудники Министерства молодёжной политики.
2. Специалисты органов местного самоуправления.
3. Сотрудники муниципальных молодёжных центров и пространств.
4. Руководители и наставники специалистов.
5. Администраторы адаптационного маршрута.
6. Методисты и владельцы базы знаний.
7. Аналитики, имеющие доступ только к обезличенной статистике.

### 3.5. Ожидаемый эффект

- единый маршрут адаптации вместо разрозненных инструкций;
- снижение количества ошибок в типовых задачах;
- ускорение поиска документов и ответственных;
- рост самостоятельности сотрудников;
- накопление доказательств практической работы;
- контролируемая нагрузка на наставников;
- единая картина прохождения маршрута;
- раннее выявление затруднений и потребности в помощи;
- формирование культуры работы от потребности молодёжи к измеримому результату.

## 5. Текущее состояние и целевая версия

### 5.1. Текущий прототип

Прототип представляет собой одностраничное статическое веб-приложение, созданное на HTML, CSS и JavaScript и опубликованное через GitHub Pages.

В прототипе:

- интерфейс работает без серверной сборки;
- профиль и настройки хранятся в `localStorage`;
- пользовательские файлы хранятся в `IndexedDB` конкретного браузера;
- аналитика доступна только в том же браузере;
- административный доступ закреплён за ранее активированным браузером и локальным ПИН-кодом;
- ИИ-агент использует локальные сценарии и поиск по данным сайта;
- предусмотрены точки подключения внешнего ИИ через backend, но полноценный серверный контур отсутствует;
- данные не синхронизируются между устройствами;
- очистка данных браузера может удалить профиль, прогресс и файлы.

### 5.2. Целевая промышленная версия

Целевая версия должна быть клиент-серверной информационной системой. Источником истины должна выступать серверная база данных, а не браузер пользователя.

Обязательные отличия целевой версии:

| Область | Прототип | Целевая версия |
|---|---|---|
| Пользователь | Локальный профиль | Зарегистрированный аккаунт |
| Авторизация | Отсутствует для пользователя | Защищённая серверная сессия |
| Администратор | Локальный ПИН | Серверная роль и усиленная аутентификация |
| Данные | В браузере | В централизованной БД |
| Файлы | IndexedDB | Защищённое объектное хранилище |
| Аналитика | Только локальная | По всем разрешённым пользователям |
| Проверка | Локальная имитация | Серверный workflow пользователь → ИИ → администратор |
| ИИ | Локальные правила | Защищённый backend, RAG и журнал решений |
| Согласия | Информационные предупреждения | Версионируемые юридические согласия |
| Аудит | Локальный журнал | Неизменяемый серверный журнал |
| Восстановление | Не предусмотрено | Резервное копирование и восстановление |

## 6. Роли и права доступа

### 6.1. Незарегистрированный посетитель

Может:

- открыть страницу входа;
- ознакомиться с назначением платформы;
- открыть политику обработки ПДн, пользовательское соглашение и сведения об ИИ;
- начать регистрацию;
- восстановить пароль;
- обратиться в поддержку.

Не может:

- просматривать внутреннюю базу знаний;
- видеть профили и прогресс пользователей;
- загружать материалы;
- пользоваться административной панелью.

### 6.2. Зарегистрированный пользователь

Может:

- управлять своим профилем;
- проходить маршрут;
- выполнять задания;
- прикреплять разрешённые подтверждения;
- запускать ИИ-предпроверку;
- отправлять задание администратору;
- получать замечания и дорабатывать результат;
- пользоваться мастерской, календарём и базой знаний;
- вести собственную карту партнёров;
- сохранять материалы;
- просматривать только свои данные и историю;
- отзывать необязательные согласия и подавать запросы по ПДн.

### 6.3. Наставник или проверяющий

Целевая дополнительная роль. Может:

- видеть назначенных ему пользователей;
- просматривать отправленные задания;
- читать заключение ИИ;
- оставлять комментарии;
- принимать задание или возвращать на доработку;
- видеть динамику назначенной группы;
- не имеет права изменять глобальные настройки и роли.

### 6.4. Администратор

Может:

- входить через отдельный защищённый административный контур;
- просматривать очередь заданий;
- видеть ИИ-заключения и приложенные материалы в пределах полномочий;
- принимать, возвращать на доработку или отклонять задания;
- управлять пользователями и назначать наставников;
- блокировать и разблокировать аккаунты;
- управлять базой знаний и версиями документов;
- управлять структурой маршрута, критериями заданий и сроками;
- просматривать аналитику;
- формировать выгрузки;
- управлять уведомлениями;
- просматривать журнал аудита в пределах полномочий.

### 6.5. Контент-редактор

Может создавать и обновлять материалы базы знаний, но не имеет доступа к персональным заданиям пользователей, если это не требуется его функциями.

### 6.6. Аналитик

Получает доступ только к агрегированной или обезличенной статистике. Не должен видеть тексты заданий, вложения и персональные профили.

### 6.7. Системный администратор

Обслуживает инфраструктуру. Доступ к содержанию пользовательских данных должен быть ограничен технической необходимостью, журналироваться и по возможности исключаться шифрованием и разделением полномочий.

### 8.1. Первый вход

1. Посетитель открывает платформу.
2. Система показывает страницу входа и кнопку регистрации.
3. До регистрации доступны ссылки на политику обработки ПДн, пользовательское соглашение, правила ИИ и контакты оператора.
4. Пользователь выбирает «Зарегистрироваться».
5. Указывает адрес электронной почты или номер телефона, создаёт пароль либо выбирает утверждённый способ единой авторизации.
6. Подтверждает контакт одноразовым кодом.
7. Знакомится с обязательными документами.
8. Отдельно подтверждает обязательное согласие на обработку ПДн. Необязательные согласия не должны быть заранее отмечены.
9. После успешной регистрации система создаёт аккаунт со статусом `ACTIVE` или `PENDING_APPROVAL`, если предусмотрено подтверждение организацией.
10. Пользователь видит приветствие руководителя и начинает настройку маршрута.

### 8.2. Настройка профиля

Пользователь заполняет:

- имя и фамилию или установленный формат отображаемого имени;
- город или муниципальное образование;
- организацию или подразделение;
- тип учреждения;
- должность — при необходимости;
- фотографию — необязательно;
- данные наставника — если назначение не выполняется администратором;
- предпочтительный канал уведомлений.

После сохранения:

- фиксируется дата старта 90-дневного маршрута;
- назначается маршрут;
- создаётся первая неделя;
- открывается экран «Мой день»;
- Искорик показывает вводное сообщение и объясняет возможности.

### 8.3. Ежедневный сценарий

1. Пользователь авторизуется.
2. Попадает на вкладку «Мой день».
3. Видит номер дня, дату, ценность недели и прогресс дня.
4. Открывает задание дня.
5. Изучает цель, ожидаемый результат, шаги и критерии.
6. Выполняет рабочее действие вне платформы или с помощью мастерской.
7. Добавляет заметку, файл или другой разрешённый результат.
8. Запускает ИИ-предпроверку.
9. Получает понятные замечания: что заполнено, чего не хватает, какие риски обнаружены.
10. При необходимости дорабатывает результат.
11. Нажимает «Отправить на проверку».
12. Задание появляется в очереди администратора вместе с ИИ-заключением.
13. Пользователь выполняет кейс-миссию и оставляет короткий вывод дня.
14. Искорик напоминает о незавершённых действиях, сроках и результате недели.

### 8.4. Проверка задания

1. После отправки статус меняется с «Черновик» на «ИИ-проверка».
2. ИИ анализирует задание по критериям и формирует предварительное заключение.
3. После завершения ИИ-анализа статус меняется на «Ожидает администратора».
4. Администратор получает уведомление и видит карточку в очереди.
5. Администратор изучает исходное задание, вложения, ИИ-заключение и риски.
6. Администратор выбирает одно из решений:
   - принять;
   - вернуть на доработку;
   - отклонить как не соответствующее условиям;
   - запросить дополнительную информацию.
7. Пользователь получает уведомление и комментарий.
8. После добавления обязательного результата и нажатия «Отправить» задание считается выполненным пользователем и включается в прогресс. Решение администратора отображается отдельно как статус проверки.
9. Все решения и изменения статусов журналируются.

### 8.5. Работа в течение недели

Пользователь:

- проходит пять или предусмотренное маршрутом количество практических заданий;
- формулирует главный результат недели;
- фиксирует три приоритета;
- записывает договорённости и ожидаемую помощь;
- добавляет события в календарь;
- использует мастерскую для подготовки рабочих материалов;
- обращается к базе знаний и ИИ-агенту;
- видит принятые, ожидающие и возвращённые задания.

### 8.6. Завершение маршрута

После выполнения и отправки всех обязательных заданий:

1. открывается финальная самодиагностика;
2. пользователь отвечает на вопросы о профессиональных предпочтениях;
3. ИИ и алгоритмический модуль анализируют ответы и подтверждённые результаты;
4. формируется профиль профессионального развития;
5. профиль содержит миссию, сильные стороны, зоны роста и рекомендации по обучению;
6. пользователь сохраняет отчёт в PDF;
7. администратор видит факт завершения маршрута;
8. система предлагает следующий индивидуальный план развития.

### 8.7. Возврат пользователя

При повторном входе с любого разрешённого устройства пользователь должен увидеть актуальное серверное состояние:

- текущий день маршрута;
- прогресс;
- статусы проверок;
- заметки и календарь;
- рабочие черновики;
- сохранённые материалы;
- карту партнёров;
- историю сообщений и уведомлений в пределах установленного срока хранения.

## 9. Требования к регистрации и авторизации

### 9.1. Регистрация пользователя

Система должна поддерживать один или несколько утверждённых способов:

- электронная почта и пароль;
- номер телефона и пароль;
- одноразовый код;
- корпоративная учётная запись;
- ЕСИА — при наличии правовых и технических оснований.

Обязательные требования:

- уникальность подтверждённого идентификатора;
- подтверждение почты или телефона;
- проверка сложности пароля;
- защита от автоматических регистраций;
- ограничение количества попыток;
- фиксация версии принятых документов;
- запрет самостоятельного выбора роли администратора;
- серверная валидация всех полей;
- возможность приглашения пользователя администратором.

### 9.2. Запрет регистрации администратора

Публичная форма не должна содержать роль «Администратор».

Административная учётная запись создаётся только:

- уполномоченным системным администратором;
- через защищённую служебную процедуру;
- на основании распоряжения или заявки;
- с обязательной фиксацией инициатора, основания и даты.

Самостоятельное повышение роли запрещено. Изменение роли требует проверки полномочий и должно попадать в журнал аудита.

### 9.3. Вход пользователя

- защищённая передача данных по HTTPS;
- безопасная серверная сессия;
- короткоживущий access token и безопасный refresh token либо серверная cookie-сессия;
- cookie с флагами `HttpOnly`, `Secure`, `SameSite`;
- защита от перебора пароля;
- уведомление о входе с нового устройства;
- возможность завершить другие сессии;
- автоматическое завершение неактивной сессии;
- восстановление доступа через подтверждённый канал.

### 9.4. Вход администратора

Для администратора обязательны:

- отдельный маршрут входа;
- двухфакторная аутентификация;
- ограничение числа попыток;
- повышенное журналирование;
- короткий срок неактивной сессии;
- повторная аутентификация перед изменением ролей, массовой выгрузкой или удалением данных;
- возможность ограничения доступа доверенными устройствами или сетью;
- запрет хранения административного секрета в клиентском JavaScript.

### 9.5. Состояния аккаунта

- `PENDING_CONFIRMATION` — контакт не подтверждён;
- `PENDING_APPROVAL` — ожидается подтверждение организации;
- `ACTIVE` — доступ разрешён;
- `BLOCKED` — временная блокировка;
- `SUSPENDED` — административная приостановка;
- `ARCHIVED` — аккаунт выведен из активной работы;
- `DELETION_REQUESTED` — обрабатывается запрос на удаление.

## 10. Подробное описание пользовательских разделов

### 10.1. Общий каркас интерфейса

На настольных экранах интерфейс содержит левую боковую панель, верхнюю панель и рабочую область. На мобильных устройствах основные вкладки размещаются в нижней навигации.

Боковая панель содержит:

- логотип;
- имя, фотографию и тип учреждения;
- процент адаптации;
- пункты основной навигации;
- количество активных заданий;
- количество сохранённых материалов;
- ссылку на помощь специалиста;
- правила работы с ИИ;
- административный вход, видимый только при наличии прав.

Верхняя панель содержит:

- название платформы на мобильном устройстве;
- статус среды;
- административный индикатор;
- быстрый переход к поиску;
- переключение графитовой и светлой темы;
- меню правил.

### 10.2. Вкладка «Мой день»

Назначение: предоставить пользователю один понятный ежедневный фокус и не перегружать его всем маршрутом сразу.

Состав:

1. Приветственный блок с обращением по имени.
2. Объяснение общественного смысла работы.
3. Три смысловых ориентира:
   - для кого выполняется работа;
   - зачем она выполняется;
   - ценность текущей недели.
4. Ежедневная рабочая панель из четырёх вкладок:
   - **Задание** — главное действие дня;
   - **Принцип** — профессиональная мысль дня;
   - **Кейс** — небольшая практическая миссия;
   - **Вывод** — короткая рефлексия.
5. Индикатор выполнения дня от 0 до 4.
6. Навигатор восьми направлений возможностей:
   - гранты;
   - форумы;
   - добровольчество;
   - патриотическое направление;
   - карьера;
   - бизнес;
   - профессиональное развитие;
   - международное направление.

Требования:

- ежедневный фокус определяется датой старта и маршрутом;
- прогресс обновляется без перезагрузки;
- рефлексия сохраняется автоматически;
- завершение кейса можно отменить;
- ссылки на внешние ресурсы открываются в новой вкладке;
- Искорик учитывает содержимое дня в ответах и напоминаниях.

### 10.3. Вкладка «Мои 90 дней»

Назначение: показать долгосрочную логику адаптации и связь заданий с профессиональной миссией.

Состав:

- текущий день и общий процент;
- манифест миссии молодёжной политики;
- временная шкала ключевых этапов;
- 3 этапа: «1–30 дней», «31–60 дней» и «61–90 дней»;
- 15 заданий на этапе «1–30 дней», 7 заданий на этапе «31–60 дней» и 15 заданий на этапе «61–90 дней»;
- тематические недели, профессиональные ценности и вопросы для рефлексии;
- результат каждой недели для молодёжи;
- итоговый вопрос о личной профессиональной миссии.

Этапы должны визуально различаться как завершённые, текущие и будущие. Даты рассчитываются от подтверждённой даты начала маршрута.

### 10.4. Вкладка «Рабочая мастерская»

Назначение: дать пользователю инструменты, с помощью которых он получает реальный рабочий результат.

#### 10.4.1. Инструмент «Мероприятие»

Пользователь выбирает одно из направлений:

1. патриотическое;
2. добровольческое;
3. культурно-досуговое;
4. спортивное;
5. образовательное;
6. творческое.

Для каждого направления показываются миссия, возможные форматы, маршрут запуска и ожидаемый итог.

Конструктор содержит две группы полей.

**Концепция:**

- целевая аудитория;
- подтверждённая потребность;
- формат;
- собственный вариант формата;
- роль участника;
- ожидаемое изменение.

**Организация:**

- количество участников;
- площадка;
- дата;
- время;
- ресурсы;
- доступность;
- безопасность;
- обратная связь;
- следующий шаг.

Система рассчитывает предварительную полноту концепции. ИИ может предложить название, описание, формат, сценарный план и рекомендации. Черновик сохраняется автоматически.

#### 10.4.2. Инструмент «Проект»

Поля:

- проблема или запрос;
- целевая аудитория;
- цель;
- команда и партнёры;
- ресурсы;
- первые шаги и сроки;
- показатели результата.

Результат — основа паспорта проекта для обсуждения с командой.

#### 10.4.3. Инструмент «Инициатива»

Поля:

- автор идеи;
- желаемое изменение;
- необходимая поддержка;
- следующий шаг и дата.

Результат — карточка сопровождения, сохраняющая авторство молодого человека или команды.

#### 10.4.4. Инструмент «Результат»

Поля:

- что сделано;
- кто и сколько участвовал;
- что изменилось;
- обратная связь;
- что сохранить или изменить.

Результат — краткая доказательная фиксация эффекта.

#### 10.4.5. «Моя рабочая неделя»

Для каждой календарной недели независимо хранятся:

- главный результат;
- три приоритета;
- договорённости;
- ожидаемая помощь.

Пользователь может переходить между предыдущими и следующими неделями, редактировать историю и видеть границы недели с понедельника по воскресенье.

#### 10.4.6. Рабочий календарь

Календарь использует реальные даты. Для даты доступны:

- краткая подпись;
- заметка;
- признак важной даты.

Требуется добавить в целевой версии:

- напоминания;
- связь с заданиями, партнёрами и мероприятиями;
- фильтры;
- экспорт в распространённый календарный формат;
- серверную синхронизацию.

### 10.5. Вкладка «База знаний»

Назначение: предоставить единое место для поиска проверенной нормативной, методической и практической информации.

На главном экране размещаются поисковая строка и шесть разделов:

1. **Нормативная база**.
2. **Рабочие материалы**.
3. **Глоссарий**.
4. **Проекты и программы**.
5. **Карта партнёров**.
6. **Структура отрасли**.

Общий поиск должен индексировать названия, описания, ключевые слова, реквизиты и разрешённое содержимое документов. Результат должен показывать тип материала, источник, дату актуализации и прямой переход к карточке.

#### 10.5.1. Нормативная база

Раздел содержит:

- федеральные документы;
- региональные документы;
- отраслевые стандарты;
- методические материалы;
- карточки первоисточников и внешние ссылки.

Карточка документа должна содержать:

- полное название;
- вид документа;
- номер и дату;
- орган-источник;
- территорию действия;
- краткое описание;
- дату публикации;
- дату последней проверки;
- статус актуальности;
- версию;
- файл или ссылку на официальный источник;
- ответственного редактора;
- историю версий.

Просроченный, отменённый или непроверенный документ должен иметь заметное предупреждение. ИИ не должен использовать такой материал как действующую норму без явной оговорки.

#### 10.5.2. Рабочие материалы

Раздел объединяет три самостоятельных подраздела.

**Шаблоны писем** — заготовки официальных, информационных, партнёрских и сопроводительных писем.
**Формы отчётов** — структуры для фиксации количественных и качественных результатов.
**Чек-листы** — пошаговые памятки, трекеры и листы планирования.

Для каждого материала предусматриваются:

- название;
- краткое назначение;
- тип и формат файла;
- размер;
- версия и дата актуализации;
- владелец;
- поиск;
- предварительный просмотр, если формат поддерживается;
- открытие;
- сохранение в личную подборку;
- скачивание с понятным названием файла.

В действующем прототипе опубликованы шесть чек-листов:

1. «Лист планирования недели»;
2. «Трекер привычки»;
3. «10 шагов к персональной ответственности»;
4. «Как составить пошаговый план персонального развития»;
5. «Направления работы наставника с молодыми людьми: от целей до результатов»;
6. «Стратегия молодёжной политики: вовлечение заинтересованных сторон».

Технические имена файлов не должны показываться вместо содержательных названий документов.

#### 10.5.3. Глоссарий

Раздел содержит отраслевые понятия, определения и пояснения.

Функции:

- алфавитная навигация;
- полнотекстовый поиск;
- фильтрация по теме;
- карточка термина;
- связанные понятия;
- указание источника определения;
- сохранение термина;
- предложение редактору исправления или дополнения.

#### 10.5.4. Проекты и программы

Раздел представляет каталог федеральных, региональных и иных программ и возможностей для молодёжи.

Карточка должна содержать:

- название;
- уровень и организатора;
- целевую аудиторию;
- направление;
- описание возможности;
- сроки;
- условия участия;
- официальный источник;
- статус актуальности;
- контакт или маршрут получения консультации.

#### 10.5.5. Карта партнёров

Назначение: помочь специалисту вести собственную рабочую сеть и историю взаимодействия.

Категории партнёров:

- органы власти;
- образовательные организации;
- некоммерческие организации;
- бизнес;
- учреждения культуры и спорта;
- медиа;
- инициативные группы;
- иные категории, настроенные администратором.

Карточка партнёра содержит:

- название;
- категорию;
- контактное лицо;
- разрешённые контактные данные;
- город или территорию;
- направления сотрудничества;
- историю взаимодействия;
- последнюю договорённость;
- следующий шаг и срок;
- связанные мероприятия и проекты.

Персональные контакты партнёров обрабатываются только при наличии правового основания. Пользователь должен быть предупреждён о запрете внесения избыточных или чувствительных сведений.

#### 10.5.6. Структура отрасли

Раздел объясняет устройство молодёжной политики и маршруты взаимодействия.

Состав:

- федеральный уровень;
- региональный уровень;
- муниципальный уровень;
- подведомственные и партнёрские организации;
- карточки учреждений;
- функции и зоны ответственности;
- контактные маршруты;
- фотогалереи пространств;
- схема эскалации вопроса.

Пользователь должен понимать, куда направить вопрос и кто принимает решение на каждом уровне.

### 10.6. Вкладка «Мои задания»

Назначение: предоставить рабочую очередь заданий маршрута и прозрачный цикл их выполнения и проверки.

Состав страницы:

- номер текущей недели;
- ценность недели;
- ожидаемый результат для молодёжи;
- срок;
- недельный прогресс;
- список заданий;
- статусы заданий;
- вход в игру «Маршрут решения»;
- вход в итоговую самодиагностику после выполнения условий.

Карточка задания должна показывать:

- название;
- описание действия;
- объяснение общественного смысла;
- ожидаемый результат;
- рекомендуемые шаги;
- критерии проверки;
- срок;
- обязательность;
- допустимые форматы подтверждения;
- текстовую заметку;
- вложения;
- историю версий;
- результат ИИ-предпроверки;
- комментарий администратора;
- статус.

#### 10.6.1. Статусы задания

| Статус | Смысл |
|---|---|
| `LOCKED` | Задание ещё недоступно |
| `AVAILABLE` | Задание доступно, но работа не начата |
| `DRAFT` | Есть несохранённая или сохранённая работа пользователя |
| `AI_REVIEW` | Выполняется ИИ-предпроверка |
| `AI_REVISION_RECOMMENDED` | ИИ обнаружил существенные пробелы, пользователь может доработать |
| `SUBMITTED` | Передано в очередь администратора; задание учтено в пользовательском прогрессе |
| `IN_REVIEW` | Администратор начал проверку |
| `REVISION_REQUIRED` | Возвращено на доработку |
| `APPROVED` | Принято администратором |
| `REJECTED` | Отклонено с обязательным обоснованием |
| `OVERDUE` | Срок истёк, задание не принято |
| `ARCHIVED` | Выведено из активного маршрута |

ИИ не имеет права самостоятельно устанавливать итоговый статус `APPROVED` или `REJECTED`, если иное не будет отдельно утверждено организацией и юридически обосновано. В основной модели окончательное решение принимает человек.

#### 10.6.2. Вложения

Пользователь может прикреплять разрешённые файлы в форматах PDF, DOCX, XLSX, PPTX, JPG, PNG и иных форматах, утверждённых администратором.

Требования:

- настраиваемый предел количества и размера файлов;
- антивирусная проверка;
- определение фактического типа файла;
- запрет исполняемых файлов;
- безопасное имя и отдельный идентификатор хранения;
- шифрование при передаче и хранении;
- журнал скачиваний;
- предварительное предупреждение не загружать лишние ПДн;
- возможность удалить черновое вложение до отправки;
- сохранение проверенной версии после отправки.

#### 10.6.3. Игра «Маршрут решения»

Игровой модуль проверяет способность отличать типовые рабочие ситуации от случаев, где необходимы решение человека, согласование или эскалация.

Функции:

- набор вопросов по тематическим блокам;
- один выбор на вопрос;
- объяснение ответа;
- итоговый балл;
- лучший результат;
- возможность повторного прохождения;
- рекомендованный порог;
- отсутствие влияния игрового балла на кадровые решения.

#### 10.6.4. Профиль профессионального развития

После выполнения условий пользователь проходит самодиагностику. Результатом являются:

- ведущая профессиональная роль;
- две дополнительные сильные роли;
- персональная миссия;
- сильные стороны;
- зоны развития;
- рекомендуемые образовательные шаги;
- PDF-отчёт.

Профиль носит рекомендательный, а не психодиагностический или кадровый характер. Пользователь должен видеть соответствующее пояснение.

### 10.7. Вкладка «Сохранённое»

Раздел объединяет личную подборку материалов:

- документы;
- шаблоны;
- чек-листы;
- термины;
- программы;
- карточки структуры отрасли;
- иные поддерживаемые сущности.

Функции:

- фильтрация по типу;
- поиск;
- сортировка по дате сохранения и названию;
- переход в исходный раздел;
- удаление из подборки;
- пустое состояние с объяснением;
- серверная синхронизация между устройствами.

### 10.8. Глобальный поиск

Поиск открывается из верхней панели и должен охватывать:

- нормативные документы;
- глоссарий;
- рабочие материалы;
- программы;
- структуру отрасли;
- пользовательские задания — только собственные;
- партнёров — только в пределах прав;
- справочные ответы Искорика.

Требования:

- поиск по части слова и словоформам русского языка;
- подсветка совпадений;
- фильтры по типу и актуальности;
- ранжирование официальных актуальных источников выше вспомогательных;
- отсутствие утечки результатов, недоступных текущей роли;
- журналирование обезличенных поисковых запросов для улучшения базы знаний;
- возможность отключить аналитическую обработку запросов, если она не обязательна.

### 10.9. Уведомления

Система должна поддерживать внутренние уведомления и, при отдельном согласии, электронную почту или push-уведомления.

События:

- назначено новое задание;
- приближается срок;
- срок пропущен;
- завершена ИИ-предпроверка;
- задание принято администратором;
- задание возвращено на доработку;
- получен комментарий;
- назначен наставник;
- обновлён важный документ;
- обнаружен вход с нового устройства;
- изменены условия или согласия.

Уведомление не должно раскрывать чувствительное содержание на экране блокировки или в теме письма.

## 11. Административная панель

### 11.1. Назначение

Административная панель является рабочим местом для сопровождения пользователей, проверки заданий, управления контентом и контроля качества платформы.

Панель не должна быть просто скрытым экраном клиентского приложения. Доступ должен проверяться сервером для каждого административного запроса.

### 11.2. Главный экран

Ключевые показатели:

- количество активных пользователей;
- новые пользователи за период;
- средний прогресс;
- количество завершивших маршрут;
- задания, ожидающие проверки;
- средний срок проверки;
- количество возвратов;
- просроченные задания;
- пользователи без активности;
- ошибки ИИ-обработки;
- документы, требующие актуализации.

Дополнительно выводится лента последних событий с фильтрами по типу, периоду, организации и пользователю.

### 11.3. Очередь проверки заданий

Администратор должен видеть таблицу или карточки со следующими полями:

- пользователь;
- организация и территория;
- неделя и название задания;
- дата отправки;
- срок;
- статус ИИ-проверки;
- краткий ИИ-вывод;
- уровень риска;
- наличие файлов;
- назначенный проверяющий;
- длительность ожидания.

Фильтры:

- статус;
- период;
- организация;
- территория;
- наставник;
- неделя маршрута;
- уровень риска;
- наличие вложений;
- просрочка.

Карточка проверки должна содержать:

1. исходную формулировку и критерии задания;
2. текст пользователя;
3. прикреплённые файлы;
4. историю предыдущих версий;
5. структурированное ИИ-заключение;
6. найденные риски и ссылки на критерии;
7. поле комментария;
8. решения «Принять», «Вернуть на доработку», «Отклонить», «Запросить сведения»;
9. историю решений;
10. сведения о проверяющем и времени действий.

Администратор должен иметь возможность не согласиться с ИИ. Такое расхождение фиксируется для контроля качества, но не требует раскрытия внутренних рассуждений модели.

### 11.4. Управление пользователями

Функции:

- поиск и фильтрация;
- просмотр разрешённого профиля;
- приглашение пользователя;
- подтверждение принадлежности к организации;
- назначение маршрута и даты старта;
- назначение наставника;
- блокировка и разблокировка;
- сброс активных сессий;
- изменение роли по защищённой процедуре;
- просмотр согласий;
- обработка запроса на выгрузку, исправление или удаление ПДн;
- экспорт минимально необходимой отчётности.

### 11.5. Управление маршрутом

Администратор с соответствующим правом может:

- создавать версии маршрута;
- определять недели, ценности и результаты;
- создавать задания;
- задавать критерии ИИ и администратора;
- указывать обязательность и срок;
- настраивать допустимые вложения;
- назначать материалы базы знаний;
- предварительно просматривать маршрут;
- публиковать новую версию;
- архивировать версию без изменения уже начатых маршрутов.

Изменение опубликованного задания не должно незаметно менять условия для уже отправленного результата. Версия задания сохраняется вместе с отправкой.

### 11.6. Управление базой знаний

Функции:

- создание и редактирование карточек;
- загрузка файлов;
- назначение категории и ключевых слов;
- установка даты проверки;
- подтверждение официального источника;
- предпросмотр;
- публикация и снятие с публикации;
- история версий;
- назначение владельца;
- массовое уведомление при критическом обновлении;
- переиндексация для поиска и RAG.

### 11.7. Аналитика

Отчёты:

- прохождение маршрута по неделям;
- воронка статусов заданий;
- средний срок выполнения и проверки;
- типовые причины возврата;
- активность по организациям и территориям;
- востребованность материалов;
- поисковые запросы без результата;
- обращения к ИИ по категориям;
- доля согласия администратора с ИИ-рекомендациями;
- технические ошибки и время ответа.

По умолчанию отчёты должны использовать агрегированные данные. Персональная детализация допускается только при наличии служебной необходимости и соответствующих прав.

### 11.8. Журнал аудита

Журнал фиксирует:

- входы и неуспешные попытки;
- создание и изменение ролей;
- просмотр и выгрузку чувствительных данных;
- изменение согласий;
- отправку и проверку заданий;
- решения администратора;
- публикацию и изменение документов;
- запросы к ИИ, идентификатор модели и версию промпта;
- системные ошибки;
- действия по удалению и восстановлению данных.

Запись содержит субъект, действие, объект, дату и время, результат, источник запроса и технический идентификатор корреляции. Пользователь с административными правами не должен иметь возможности незаметно удалить или переписать аудит.

## 12. ИИ-агент «Искорик»

### 12.1. Роль ИИ в платформе

Искорик — не декоративный чат-бот, а встроенный цифровой помощник, связанный с контекстом маршрута, базой знаний и процессом проверки заданий.

Он выполняет четыре роли:

1. **Навигатор** — помогает найти раздел, документ, инструмент или следующий шаг.
2. **Методический помощник** — объясняет понятия и помогает структурировать рабочий материал.
3. **Тренер** — задаёт уточняющие вопросы, напоминает о критериях и поддерживает рефлексию.
4. **Предварительный проверяющий** — анализирует результат задания до передачи администратору.

ИИ должен усиливать самостоятельность пользователя, а не подменять его профессиональное решение.

### 12.2. Возможности диалога

Искорик должен уметь:

- отвечать на вопросы о работе платформы;
- находить материалы и давать ссылки на них;
- объяснять термины простым языком;
- подсказывать последовательность действий;
- помогать сформулировать цель, ожидаемый результат и показатели;
- давать обратную связь по черновику;
- предлагать варианты, а не выдавать непроверенную информацию как факт;
- учитывать текущую вкладку, неделю и задание;
- предлагать обращение к человеку при высоком риске или недостатке данных.

Ответы по нормативным вопросам должны сопровождаться ссылками на использованные источники и датой их актуальности. При отсутствии подтверждённого источника ИИ сообщает об ограничении.

### 12.3. Сценарий ИИ-проверки задания

1. Пользователь добавляет результат и нажимает «Проверить с Искориком» либо «Отправить на проверку».
2. Backend создаёт неизменяемую версию отправки.
3. Файлы проходят антивирусную и техническую проверку.
4. Сервис извлекает разрешённый текст из файлов.
5. До передачи внешней модели выполняется классификация данных и, где возможно, маскирование идентификаторов и лишних ПДн.
6. Оркестратор получает версию задания, критерии, текст пользователя, разрешённые фрагменты файлов и релевантные материалы базы знаний.
7. ИИ оценивает каждый критерий отдельно.
8. Формируется структурированное заключение.
9. Автоматические правила проверяют формат и допустимость ответа модели.
10. Пользователю показывается понятная предварительная обратная связь.
11. При отправке администратору исходные материалы и ИИ-заключение помещаются в очередь.
12. Администратор принимает окончательное решение.

### 12.4. Структура ИИ-заключения

Заключение должно храниться в структурированном виде и включать:

- идентификатор задания и версии отправки;
- итоговую рекомендацию: `READY_FOR_REVIEW`, `REVISION_RECOMMENDED`, `MANUAL_REVIEW_REQUIRED`;
- оценку полноты по каждому критерию;
- обнаруженные сильные стороны;
- список недостающих элементов;
- проверяемые замечания со ссылкой на конкретный фрагмент;
- риски: ПДн, небезопасное содержание, недостоверная ссылка, несоответствие задаче;
- вопросы пользователю;
- краткое резюме для администратора;
- уровень уверенности;
- использованные источники;
- идентификатор модели;
- версию системной инструкции и критериев;
- дату и длительность обработки.

### 12.5. Принципы оценки

ИИ оценивает не личность пользователя, а конкретный материал по заранее опубликованным критериям.

Запрещено:

- делать выводы о благонадёжности, политических взглядах, здоровье, этнической принадлежности или иных чувствительных характеристиках;
- выставлять скрытый кадровый рейтинг;
- принимать решение об увольнении, премировании или профессиональной пригодности;
- снижать результат за стиль речи, не влияющий на критерии;
- придумывать факты или ссылки;
- использовать материалы одного пользователя в ответе другому;
- обучать внешнюю модель на пользовательских данных без отдельного законного основания и договора.

### 12.6. Передача результата администратору

В административной очереди ИИ-блок должен визуально отделяться от исходной работы пользователя и содержать пометку **«Предварительная рекомендация ИИ. Итоговое решение принимает человек»**.

Администратор видит:

- оригинальный текст и файлы;
- краткое резюме;
- оценку по критериям;
- замечания с привязкой к фрагментам;
- риски;
- источники;
- уверенность модели;
- историю повторных проверок.

Администратор может отметить рекомендацию полезной или ошибочной и указать категорию расхождения. Эти данные используются для оценки качества, но не для автоматического обучения без утверждённого процесса.

### 12.7. Маршрутизация рисков

ИИ должен переводить материал на обязательную ручную проверку, если:

- обнаружены возможные ПДн третьих лиц;
- материал содержит сведения о несовершеннолетних;
- есть признаки конфиденциальной информации;
- требуется толкование НПА;
- обнаружено противоречие источников;
- уверенность ниже установленного порога;
- файл не удалось корректно прочитать;
- запрос связан с безопасностью, здоровьем, конфликтом или правонарушением;
- пользователь просит принять решение вместо ответственного лица.

### 12.8. RAG и источники знаний

ИИ должен отвечать на основе утверждённого индекса знаний. В индекс включаются только опубликованные и разрешённые материалы.

Для каждого фрагмента хранятся:

- исходный документ;
- версия;
- раздел или страница;
- дата актуальности;
- уровень доступа;
- владелец;
- контрольная сумма.

Поиск обязан учитывать права пользователя до формирования ответа. Документ, недоступный пользователю, не должен попадать ни в контекст модели, ни в цитату, ни в список источников.

### 12.9. Защита ИИ-контура

- запросы к модели выполняются только через backend;
- ключи API не передаются в браузер;
- системные инструкции защищаются от изменения пользователем;
- входной контент считается недоверенным;
- применяются меры против prompt injection из файлов и документов;
- инструменты ИИ работают по белому списку;
- модель не получает прямой произвольный доступ к БД;
- ответы проходят схематическую и содержательную валидацию;
- устанавливаются лимиты запросов, размера и времени;
- предусмотрен отказоустойчивый режим без ИИ;
- содержание диалогов хранится только установленный срок;
- поставщик ИИ должен обеспечивать договорные гарантии конфиденциальности и запрет обучения на данных заказчика.

### 12.10. Прозрачность для пользователя

До первого использования ИИ пользователь должен увидеть:

- что ответ формируется автоматически;
- какие данные могут быть переданы модели;
- для чего они используются;
- что нельзя загружать;
- как долго хранится история;
- как обратиться к человеку;
- что итоговую проверку задания выполняет администратор;
- как сообщить об ошибочном ответе.

### 12.11. Метрики качества ИИ

- доля успешно обработанных запросов;
- медианное время ответа;
- доля ответов с корректными источниками;
- доля заключений, изменённых администратором;
- причины расхождений;
- доля ложных предупреждений о рисках;
- доля пропущенных рисков по контрольной выборке;
- пользовательская оценка полезности;
- количество эскалаций человеку;
- отсутствие межпользовательских утечек в тестах.

Запуск новых моделей или промптов выполняется после тестирования на утверждённом обезличенном наборе примеров и сравнения с предыдущей версией.

## 13. Обработка персональных данных

### 13.1. Общие положения

Обработка ПДн должна проектироваться с учётом применимого законодательства Российской Федерации, в том числе требований Федерального закона № 152-ФЗ «О персональных данных», подзаконных актов, требований к локализации и внутренних документов оператора.

Окончательный состав мер, уровень защищённости и тексты юридических документов определяются оператором совместно с юристом и специалистом по информационной безопасности до промышленного запуска.

### 13.2. Оператор и цели обработки

На страницах регистрации и политики должны быть указаны полное наименование и контакты оператора ПДн.

Цели обработки разделяются как минимум на:

- создание и обслуживание аккаунта;
- идентификацию и управление доступом;
- прохождение профессионального маршрута;
- проверку заданий;
- коммуникацию и уведомления;
- техническую поддержку;
- обеспечение безопасности;
- формирование обязательной отчётности;
- улучшение платформы на основе агрегированных данных;
- использование ИИ-функций.

Для каждой цели определяются правовое основание, состав данных, операции, получатели, срок хранения и порядок удаления.

### 13.3. Категории обрабатываемых данных

В зависимости от утверждённого процесса могут обрабатываться:

- ФИО или отображаемое имя;
- электронная почта;
- телефон;
- организация, должность и территория;
- фотография профиля;
- сведения о наставнике;
- прогресс, ответы, заметки и результаты заданий;
- загруженные пользователем файлы;
- календарные записи и рабочие черновики;
- контакты партнёров;
- история сообщений с ИИ;
- технические данные: IP-адрес, устройство, время входа, идентификатор сессии, журнал событий;
- согласия и история их изменения.

Специальные категории и биометрические ПДн не должны собираться без отдельной необходимости, правового основания и специальных мер. Фотография профиля по умолчанию используется как визуальное оформление и не должна применяться для биометрической идентификации.

### 13.4. Минимизация данных

- обязательными являются только сведения, без которых невозможно предоставить функцию;
- необязательные поля явно помечаются;
- нельзя требовать контакты третьих лиц без необходимости;
- свободные поля сопровождаются предупреждением не указывать лишние ПДн;
- содержимое файлов анализируется на наличие идентификаторов и чувствительных данных;
- аналитика по возможности строится на обезличенных данных;
- ИИ получает минимально необходимый контекст.

### 13.5. Согласия

Согласие должно быть конкретным, информированным, сознательным и однозначным. Система хранит:

- вид согласия;
- версию текста;
- дату и время;
- способ подтверждения;
- пользователя;
- техническое подтверждение;
- дату отзыва.

Отдельные согласия предусматриваются, если они необходимы, для:

- необязательных рассылок;
- обработки фотографии;
- использования внешнего ИИ-провайдера;
- передачи данных отдельному третьему лицу;
- публикации материалов пользователя.

Отзыв необязательного согласия должен быть доступен из профиля и не должен необоснованно блокировать основные функции.

### 13.6. Права субъекта ПДн

Пользователь должен иметь возможность:

- узнать, какие данные о нём обрабатываются;
- получить копию данных в понятном формате;
- исправить неточные сведения;
- отозвать согласие;
- запросить ограничение или прекращение обработки в применимых случаях;
- запросить удаление данных с учётом обязательных сроков хранения;
- обжаловать решение и обратиться к оператору;
- получить информацию об автоматизированной обработке.

Все запросы регистрируются, получают срок исполнения и ответственного.

### 13.7. Сроки хранения

До запуска оператор утверждает матрицу сроков. В ней отдельно указываются сроки для:

- аккаунта;
- результатов заданий;
- файлов;
- административных решений;
- ИИ-диалогов и заключений;
- журналов безопасности;
- согласий;
- резервных копий;
- обезличенной статистики.

По окончании срока данные удаляются или необратимо обезличиваются. Удаление должно распространяться на поисковые индексы, векторное хранилище, временные файлы и резервные копии по установленному циклу.

### 13.8. Передача данных третьим лицам

Перед подключением хостинга, почтового сервиса, аналитики, антивируса или ИИ-провайдера оператор обязан:

- определить роль поставщика;
- заключить необходимые договоры и поручения;
- проверить место обработки и хранения;
- ограничить цели и состав данных;
- запретить использование данных для обучения моделей и рекламы без отдельного основания;
- определить порядок удаления;
- оценить трансграничную передачу;
- раскрыть существенных получателей в документах для пользователя.

### 13.9. Данные несовершеннолетних и третьих лиц

Платформа предназначена прежде всего для специалистов, однако задания могут описывать работу с молодыми людьми. Поэтому:

- запрещается без основания загружать списки участников, копии документов и сведения о здоровье;
- примеры рекомендуется обезличивать;
- документы с данными несовершеннолетних направляются на отдельный защищённый процесс либо не принимаются;
- ИИ должен предупреждать о найденных персональных идентификаторах;
- администратор должен иметь возможность удалить ошибочно загруженный файл по регламенту.

### 13.10. Локализация и размещение

Архитектура и выбранные поставщики должны обеспечивать выполнение применимых требований к записи, систематизации, накоплению, хранению и извлечению ПДн граждан Российской Федерации. Фактические площадки, резервные копии и каналы передачи документируются до ввода в эксплуатацию.

## 14. Требования к информационной безопасности

### 14.1. Базовые принципы

- безопасность по умолчанию и на этапе проектирования;
- минимальные привилегии;
- разделение ролей;
- запрет доверия клиентской стороне;
- многоуровневая защита;
- минимизация данных;
- журналируемость значимых действий;
- регулярное обновление зависимостей;
- безопасное поведение при отказе.

### 14.2. Защита приложений

Необходимо предусмотреть защиту от актуальных классов веб-угроз, включая:

- SQL/NoSQL injection;
- XSS;
- CSRF;
- SSRF;
- подмену и фиксацию сессии;
- обход авторизации;
- IDOR;
- загрузку вредоносных файлов;
- массовое назначение полей;
- утечку секретов;
- чрезмерную выдачу данных API;
- перебор учётных данных;
- злоупотребление ИИ-интерфейсом.

Обязательны серверная валидация, параметризованные запросы, контекстное экранирование, CSP, безопасные HTTP-заголовки, rate limiting и проверка права на каждый объект.

### 14.3. Шифрование и секреты

- только HTTPS с актуальной конфигурацией TLS;
- шифрование БД и резервных копий на уровне инфраструктуры;
- отдельная защита наиболее чувствительных полей при необходимости;
- пароли хранятся только как стойкие адаптивные хеши с солью;
- ключи и пароли сервисов хранятся в менеджере секретов;
- секреты не включаются в репозиторий, логи, клиентский код и резервные выгрузки;
- ротация ключей и регламент аварийной замены.

### 14.4. Контроль доступа

- RBAC с возможностью ограничения по организации или территории;
- проверка прав на backend независимо от видимости кнопок;
- принцип запрета по умолчанию;
- отдельные разрешения на просмотр, изменение, проверку, экспорт и управление ролями;
- периодическая ревизия административных аккаунтов;
- немедленное прекращение доступа при увольнении или отзыве полномочий;
- запрет общих административных учётных записей.

### 14.5. Работа с файлами

- загрузка во временную карантинную область;
- проверка антивирусом;
- проверка MIME-типа и сигнатуры;
- переименование и исключение исполнения;
- выдача через авторизованный endpoint или краткоживущую подписанную ссылку;
- запрет индексации поисковыми системами;
- отсутствие прямых публичных URL пользовательских файлов;
- журнал доступа;
- очистка метаданных изображений при необходимости.

### 14.6. Мониторинг и инциденты

Система должна собирать технические метрики и события безопасности без избыточного содержимого пользовательских материалов.

Необходимо разработать регламент:

- обнаружения инцидента;
- классификации и эскалации;
- изоляции;
- сохранения доказательств;
- восстановления;
- уведомления ответственных и субъектов в установленных случаях;
- анализа причин;
- предотвращения повторения.

### 14.7. Проверки перед запуском

- моделирование угроз;
- анализ требований по ПДн;
- статический анализ кода;
- анализ зависимостей и секретов;
- динамическое тестирование;
- тестирование разграничения доступа;
- тест загрузки файлов;
- тесты ИИ на утечки и prompt injection;
- независимый аудит или тестирование на проникновение в согласованном объёме;
- устранение критических и высоких уязвимостей до запуска.

## 15. Целевая техническая архитектура

### 15.1. Общая схема

```text
Браузер / мобильный браузер
          │ HTTPS
          ▼
Web Application Firewall / Reverse Proxy
          │
          ├── Frontend веб-приложение
          │
          └── Backend API
                ├── Сервис аутентификации и RBAC
                ├── Сервис маршрута и заданий
                ├── Сервис проверки и уведомлений
                ├── Сервис базы знаний и поиска
                ├── Сервис файлов
                ├── ИИ-оркестратор
                │     ├── RAG / векторный индекс
                │     ├── модуль маскирования ПДн
                │     └── разрешённый поставщик модели
                ├── Реляционная база данных
                ├── Объектное файловое хранилище
                ├── Очередь фоновых задач
                ├── почтовый / push-сервис
                └── аудит, мониторинг и резервное копирование
```

### 15.2. Frontend

Frontend должен:

- реализовывать адаптивный интерфейс;
- обращаться к данным только через защищённый API;
- не хранить секреты;
- использовать локальное хранилище только для некритичных настроек и безопасного кеша;
- поддерживать восстановление после сетевой ошибки;
- показывать состояние загрузки, успеха и ошибки;
- не считать скрытие элемента механизмом авторизации;
- поддерживать современные версии распространённых браузеров.

Допускается развитие текущего JavaScript-прототипа либо перенос на утверждённый компонентный frontend-стек. Решение фиксируется на этапе проектирования.

### 15.3. Backend API

Backend отвечает за:

- регистрацию и сессии;
- авторизацию каждого запроса;
- бизнес-правила маршрута;
- сохранение версий заданий;
- workflow проверки;
- выдачу файлов;
- административные операции;
- поиск;
- уведомления;
- ИИ-оркестрацию;
- аудит;
- применение сроков хранения.

API версионируется. Ошибки возвращаются в едином формате с кодом, безопасным сообщением и идентификатором корреляции.

### 15.4. База данных

Рекомендуется транзакционная реляционная СУБД. База должна обеспечивать:

- целостность связей;
- миграции схемы;
- резервное копирование;
- репликацию при необходимости;
- аудит критичных изменений;
- индексы для типовых выборок;
- хранение временных меток в UTC с отображением в локальном часовом поясе.

### 15.5. Файловое хранилище

Файлы хранятся отдельно от основной БД. В БД сохраняются метаданные, владелец, контрольная сумма, статус проверки, уровень доступа и ссылка на внутренний объект.

Публичные методические материалы и приватные пользовательские вложения должны располагаться в логически или физически разделённых областях.

### 15.6. Очередь фоновых задач

Через очередь выполняются:

- антивирусная проверка;
- извлечение текста;
- ИИ-анализ;
- индексация знаний;
- отправка уведомлений;
- формирование PDF и крупных отчётов;
- удаление по срокам;
- повтор временно неуспешной операции.

Повтор задачи должен быть идемпотентным и не создавать двойное решение или уведомление.

### 15.7. Поиск

Для первой версии допускается полнотекстовый поиск средствами основной СУБД. При росте объёма может применяться выделенный поисковый движок.

Векторный индекс ИИ не заменяет пользовательский поиск и должен наследовать уровни доступа и версии источников.

### 15.8. Окружения

Необходимо иметь раздельные среды:

- локальная разработка;
- тестовая;
- предпромышленная;
- промышленная.

Промышленные ПДн не копируются в тестовые среды. Для тестирования используются синтетические или обезличенные данные.

## 17. Требования к API и интеграциям

### 17.1. Группы API

Минимально необходимы endpoints или эквивалентные операции для:

- `/auth` — регистрация, вход, подтверждение, восстановление, выход;
- `/me` — профиль, настройки, согласия, сессии;
- `/routes` — доступный маршрут и недели;
- `/tasks` — задания, черновики, отправки, статусы;
- `/files` — загрузка, проверка, скачивание, удаление;
- `/reviews` — ИИ- и человеческие проверки;
- `/knowledge` — поиск и карточки материалов;
- `/workshop` — рабочие черновики;
- `/calendar` — календарные записи;
- `/partners` — личная карта партнёров;
- `/saved` — личная подборка;
- `/assistant` — диалоги и ИИ-операции;
- `/notifications` — уведомления;
- `/admin` — защищённые административные операции;
- `/audit` — разрешённый просмотр журнала.

### 17.2. Требования к контрактам

- документирование через OpenAPI или эквивалент;
- единые форматы дат, пагинации и ошибок;
- ограничение размера запроса;
- серверная фильтрация полей по роли;
- идемпотентность критичных операций;
- optimistic locking или иной контроль конкурентных изменений;
- trace/correlation ID;
- версионирование несовместимых изменений;
- автоматические контрактные тесты.

### 17.3. Возможные интеграции

- корпоративный провайдер идентификации;
- ЕСИА при необходимости;
- почтовый сервис;
- push-сервис;
- антивирус;
- объектное хранилище;
- система мониторинга;
- утверждённый ИИ-провайдер;
- календарные системы;
- официальный реестр или источник документов.

Каждая интеграция должна иметь тайм-аут, повтор безопасных операций, мониторинг, обработку недоступности и документированный объём передаваемых данных.

## 19. Нефункциональные требования

### 19.1. Производительность

Рекомендуемые стартовые значения: RPO не более 24 часов, RTO не более 8 часов; перед запуском они должны быть согласованы с заказчиком.

### 19.4. Масштабируемость

Архитектура должна позволять увеличивать число пользователей, документов и ИИ-задач без переработки пользовательской логики. Ресурсоёмкая ИИ-обработка отделяется от синхронного API очередью.

Поддерживаются две последние стабильные версии Chromium-based браузеров, Firefox и Safari, если иное не определено заказчиком. Проверяется работа на актуальных Android и iOS браузерах.

## 20. Бизнес-правила

1. Дата маршрута определяется сервером и доступна для изменения только уполномоченной роли.
2. Будущая неделя не открывается раньше правила маршрута, кроме административного назначения.
3. Задание считается выполненным для пользовательского прогресса после обязательного подтверждения и статуса `SUBMITTED`; статусы `APPROVED` и `REVISION_REQUIRED` отдельно отражают результат проверки.
4. Для отправки требуется хотя бы один предусмотренный результат: заметка, файл, форма или ссылка.
5. ИИ-проверка не заменяет решение администратора.
6. При возврате создаётся новая версия результата; предыдущая остаётся в истории.
7. Администратор обязан указать комментарий при возврате или отклонении.
8. Пользователь видит собственные данные и явно доступные материалы.
9. Наставник видит только назначенных пользователей.
10. Документ без подтверждённой актуальности маркируется и не цитируется ИИ как безусловно действующий.
11. Изменение опубликованной версии маршрута не переписывает историю действующих пользователей.
12. Удаление материала из публикации не удаляет аудит его использования.
13. Все административные решения журналируются.
14. Экспорт ПДн доступен только ролям с отдельным разрешением.
15. Пользователь может обратиться к человеку на любом этапе взаимодействия с ИИ.

## 22. Миграция из действующего прототипа

### 22.1. Что подлежит переносу

- визуальная концепция и структура навигации;
- контент маршрута;

### 22.2. Локальные данные пользователей

Данные существующего прототипа находятся в браузерах и не могут автоматически считаться серверными аккаунтами.

Если требуется перенос, должен быть создан отдельный пользовательский сценарий:

1. регистрация и вход;
2. локальное обнаружение данных;
3. показ состава импортируемой информации;
4. отдельное подтверждение пользователя;
5. серверная валидация;

7. отчёт об успехе или ошибках;
8. предложение удалить локальную копию после проверки.

Локальный признак администратора и локальный ПИН переносить запрещено.

### 22.3. Публикация материалов

Перед миграцией каждый материал должен получить владельца, тип доступа, версию, дату проверки и статус. Файлы без понятного происхождения или прав на использование не публикуются.

### 23.1. Виды тестирования

- модульное;

### 23.2. Обязательные сквозные сценарии

1. Регистрация → подтверждение → согласия → профиль → первый день.
2. Вход на другом устройстве → получение актуального прогресса.
3. Черновик задания → файл → ИИ-проверка → отправка → очередь администратора.
4. Возврат на доработку → новая версия → повторная ИИ-проверка → принятие.
5. Поиск документа → проверка актуальности → сохранение → открытие из «Сохранённого».
6. Создание мероприятия в мастерской → автосохранение → повторное открытие.
7. Создание партнёра → история контакта → следующий шаг.
8. Восстановление пароля и завершение других сессий.
9. Попытка пользователя открыть административный API → отказ.
10. Попытка наставника открыть неназначенного пользователя → отказ.
11. Загрузка вредоносного или запрещённого файла → карантин и безопасное сообщение.
12. ИИ-запрос с инструкцией из вложения обойти правила → отсутствие обхода.
13. Недоступность ИИ → сохранение задания и возможность ручной проверки.
14. Отзыв необязательного согласия → прекращение соответствующей обработки.
15. Запрос выгрузки и удаления данных → контролируемое исполнение и аудит.

### 23.3. Тестирование ИИ

Набор должен включать:

- полные и неполные задания;
- противоречивые данные;
- неверные ссылки;
- ПДн в тексте и файле;
- данные несовершеннолетних;
- prompt injection;
- попытку получить чужие данные;
- запрос правового решения;
- грубый или неоднозначный текст;
- скан низкого качества;
- документ на неподдерживаемом языке;
- отсутствие релевантного источника.

Эталонные ожидания утверждаются методистом, администратором и специалистом по безопасности.

## 24. Критерии приёмки

Промышленная версия считается готовой к приёмке, если одновременно выполнены следующие условия.

### 24.1. Аккаунты и доступ

- пользователь может зарегистрироваться и подтвердить контакт;
- обязательные согласия версионируются;
- пользователь может войти, выйти и восстановить доступ;
- административная регистрация недоступна публично;
- администратор входит с двухфакторной аутентификацией;
- все проверенные сценарии обхода ролей завершаются отказом.

### 24.2. Пользовательская функциональность

- доступны все основные вкладки и вложенные разделы;
- прогресс и данные синхронизируются между двумя устройствами;
- черновики не теряются после обновления страницы;
- поиск находит утверждённые материалы;
- сохранённое открывает исходную сущность;
- мастерская, календарь и карта партнёров сохраняют данные серверно;
- итоговый профиль и PDF формируются после выполнения условий.

### 24.3. Проверка заданий и ИИ

- пользователь может создать результат и прикрепить безопасный файл;
- ИИ формирует структурированное заключение по критериям;
- задание и заключение появляются у администратора;
- администратор видит оригинал, версию, источники и риски;
- администратор может принять или вернуть работу;
- пользователь получает решение и комментарий;
- ИИ не устанавливает итоговое принятие;
- при отказе ИИ задание не теряется и доступна ручная обработка;
- тесты не выявляют доступ к чужим заданиям или источникам.

### 24.4. Персональные данные и безопасность

- опубликованы утверждённые юридические документы;
- реализованы запросы субъекта ПДн;
- файлы не доступны по постоянным публичным ссылкам;
- секреты отсутствуют в клиентском коде и репозитории;
- критичные действия попадают в аудит;
- проведены резервное копирование и контрольное восстановление;
- устранены критические и высокие уязвимости;
- поставщики и места обработки документированы;
- сроки хранения технически реализованы.

### 24.5. Качество интерфейса

- ключевые пути проходят на смартфоне и компьютере;
- нет блокирующих ошибок в поддерживаемых браузерах;
- интерфейс работает с клавиатуры;
- ошибки объясняют дальнейшие действия;
- состояния загрузки и фоновой ИИ-проверки видимы;
- русские названия файлов и материалов отображаются корректно.

## 28. Риски и ограничения

| Риск | Последствие | Мера |
|---|---|---|
| Пользователь загружает лишние ПДн | Нарушение принципа минимизации | Предупреждения, DLP/PII-проверка, регламент удаления |
| ИИ даёт неверную оценку | Ошибочная рекомендация | Человек принимает решение, критерии, источники, мониторинг |
| НПА устаревает | Неверная консультация | Владелец, дата проверки, статус и автоматические напоминания |
| Администратор перегружен | Долгая проверка | Очередь, приоритеты, назначение и аналитика SLA |
| Компрометация аккаунта | Утечка данных | MFA администратора, защита сессий, уведомления |
| Поставщик ИИ недоступен | Задержка обработки | Асинхронная очередь и ручной режим |
| Внешняя модель использует данные | Неконтролируемая обработка | Договорный запрет обучения, минимизация, разрешённый контур |
| Очистка браузера | Потеря данных прототипа | Серверное хранение и контролируемая миграция |
| Ошибка в разграничении | Межпользовательская утечка | Серверный RBAC, объектные проверки, автотесты |
| Низкое качество скана | Ошибка извлечения | Маркировка уверенности и ручная проверка |
| Несогласованные критерии | Непредсказуемая оценка | Версионирование и утверждение методистом |
| Скрытое применение ИИ | Недоверие и правовой риск | Прозрачная маркировка и информация об обработке |

## 29. Показатели успешности после запуска

Через согласованный пилотный период оцениваются:

- доля пользователей, завершивших настройку профиля;
- доля активных пользователей по неделям;
- доля завершивших 90-дневный маршрут;
- среднее время от отправки до решения;
- доля заданий, принятых после первой отправки;
- доля доработок после подсказки ИИ до передачи администратору;
- удовлетворённость пользователей;
- удовлетворённость администраторов;
- востребованность мастерской и базы знаний;
- число запросов без найденного ответа;
- качество и актуальность источников;
- количество подтверждённых инцидентов и утечек;
- доступность и скорость платформы.

ИИ нельзя оценивать только количеством автоматически обработанных заданий. Основными показателями должны быть полезность, точность, безопасность, объяснимость и снижение времени администратора без ухудшения качества.
